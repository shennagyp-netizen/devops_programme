DAY 4 — CI/CD + TERRAFORM + CLOUD

EPISODE D4.1 — Git as a Production Workflow

Speaker A: Git becomes a DevOps tool when history, review, artifacts, and rollback matter.

Speaker B: I already use Git. What changes?

Speaker A: The change is operational accountability. A production deployment should be traceable to a reviewed change and a reproducible artifact.

Speaker A: Think of a legal document. You care about versions, approvals, and exactly which version was signed. Production software needs the same discipline.

Speaker A: Real-life example: if a bank asks which contract version was applied yesterday, 'I think it was the latest one' is not a satisfactory answer.

Speaker A: Lab: create a branch, commit a change, inspect the diff, tag a release, and practice reverting to a known-good version.



EPISODE D4.2 — CI/CD Mental Model

Speaker A: CI/CD is a controlled path from source code to running software.

Speaker B: The path is more important than the YAML.

Speaker A: Exactly. Source enters, tests run, an artifact is built, security and policy checks run, and deployment is promoted through environments.

Speaker A: Real-life analogy: an airport. You do not let every passenger directly onto the runway. There are identity checks, screening, gates, and controlled movement.

Speaker B: So production is the runway.

Speaker A: Correct. You want fewer surprises there.

Speaker A: Lab: design the pipeline on paper first, then implement a minimal GitHub Actions workflow.



EPISODE D4.3 — GitHub Actions

Speaker A: Now turn the pipeline into executable automation.

Speaker B: Workflow, job, step, runner.

Speaker A: Think of a factory. The workflow is the production order, jobs are workstations, steps are operations, and runners are machines executing them.

Speaker A: Artifacts are the packaged outputs that move between stages.

Speaker A: Real-life example: a bakery does not ask a different employee to guess the recipe every morning. The process is written down and reproducible.

Speaker A: Lab: test, build, package, and publish a container artifact.

Speaker B: And secrets?

Speaker A: Credentials should enter securely at the boundary, not be baked into source or artifacts.



EPISODE D4.4 — Infrastructure as Code

Speaker A: Infrastructure becomes code when the intended environment is described declaratively and changes become reviewable.

Speaker B: Like architecture diagrams, but executable.

Speaker A: Exactly, with the important addition that state and lifecycle matter.

Speaker A: Real-life analogy: building permits and construction plans. The document describes what should exist; construction changes reality.

Speaker A: Real-life example: if a cloud environment can only be recreated by clicking through someone's memory, your infrastructure is a story, not a system.

Speaker A: Lab: define a small network or service in Terraform and inspect the plan before applying.



EPISODE D4.5 — Terraform Lifecycle

Speaker A: Terraform's important loop is init, plan, review, apply, observe.

Speaker B: And state?

Speaker A: State is part of Terraform's knowledge about what it manages. Drift means reality changed outside that expected path.

Speaker A: Think of inventory management. If the spreadsheet says ten devices exist and the warehouse actually contains eight, the discrepancy is operationally important.

Speaker A: Real-life example: manual cloud console changes create exactly this kind of drift.

Speaker A: Lab: apply an environment, change one property manually, then use plan to discover the difference.



EPISODE D4.6 — Cloud Primitives

Speaker A: Cloud vendors package familiar primitives into managed services: compute, networking, storage, identity, load balancing, databases, queues and caches.

Speaker B: So I should learn the concepts before memorizing service names.

Speaker A: Absolutely. Otherwise you become excellent at flash cards and mediocre at architecture.

Speaker A: Real-life example: every city needs roads, warehouses, electricity, addresses, security and public transport. Different cities give them different names and implementations. Cloud providers do the same with infrastructure primitives.

Speaker A: We will map concepts to AWS examples only after the mental model is clear.

Speaker A: Lab: take one reference application and identify every primitive it requires, what owns it, what can fail, and what it costs operationally.
