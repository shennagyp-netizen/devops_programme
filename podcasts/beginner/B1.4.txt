Speaker A: We have a small application. It works on one laptop.

Speaker B: And now we want it to work on another laptop without spending two days asking what was installed.

Speaker A: Exactly. That makes the diagnosis easier to test.

Speaker A: Let's keep that tied to the actual problem.

Speaker B: This is where containers come in.

Speaker A: Yes, but I don't want to start with the word Docker.

Speaker B: Good. We can check that without changing everything.

Speaker B: Now say what evidence would confirm that.

Speaker A: Start with the problem.

Speaker B: A program depends on its environment.

Speaker A: Right. Now we have a concrete prediction.

Speaker A: That gives us a useful next test.

Speaker B: Runtime version. Libraries. Files. Environment variables. Network settings. Maybe system tools.

Speaker A: Exactly. Keep the recovery condition in the plan.

Speaker A: I would not change the system before checking that.

Speaker B: So "it works on my machine" is really saying "my machine has a set of conditions that your machine may not have."

Speaker A: That's the problem.

Speaker B: Give me a real-life example.

Speaker A: Two cooks follow the same recipe.

Speaker B: One kitchen has the right oven and tools. The other does not.

Speaker A: Right. That is a safer way to reason about it.

Speaker B: Same recipe. Different result.

Speaker A: Exactly. Now compare that with the known-good state.

Speaker B: So we want a repeatable kitchen.

Speaker A: That's the idea.

Speaker B: And the container is the kitchen?

Speaker A: A very rough analogy. The actual container is an isolated process environment, not a tiny virtual computer.

Speaker B: That's the part people get wrong.

Speaker A: Yes. A container shares the host kernel.

Speaker B: So it is lighter than a full virtual machine.

Speaker A: Often, yes.

Speaker B: Let's build the model.

Speaker A: An image is a packaged application environment.

Speaker B: Code, dependencies, filesystem layers, configuration defaults.

Speaker A: Right. That tells us which layer to inspect next.

Speaker B: A container is a running instance of that image.

Speaker A: Exactly. I want the observation before the fix.

Speaker B: So image is the package, container is the running thing.

Speaker A: Good.

Speaker B: Like recipe versus cooking.

Speaker A: Good.

Speaker B: Don't say the container is the recipe.

Speaker A: Thank you.

Speaker B: We are improving.

Speaker A: Slowly.

Speaker B: What problem does process isolation solve?

Speaker A: It lets us control what a process can see and use. Containers can have their own filesystem view, process view, network setup and resource limits.

Speaker B: So two applications can run on one machine without pretending they have the whole machine to themselves.

Speaker A: Exactly.

Speaker B: But they still share the host kernel.

Speaker A: Right.

Speaker B: Which means containers are not magic walls.

Speaker A: Very important.

Speaker B: Give me the first lab.

Speaker A: Run:

Speaker A: docker run --rm nginx:alpine nginx -t

Speaker B: What does that prove?

Speaker A: It proves we can start a container from an image and run a command inside it.

Speaker B: And --rm removes it after the command finishes.

Speaker A: Correct.

Speaker B: So containers are often short-lived.

Speaker A: Some are. Long-running services are still just processes inside containers.

Speaker B: That's a useful point.

Speaker A: The container runtime starts and manages the process. The process is what actually does the work.

Speaker B: So if the process inside the container crashes, the container can stop.

Speaker A: Yes.

Speaker B: And if Kubernetes later comes in, Kubernetes can notice that and replace the workload.

Speaker A: Exactly. We are building the layers now.

Speaker B: Container first. Orchestrator later.

Speaker A: Right.

Speaker B: What about files?

Speaker A: Important question. The container filesystem is usually tied to the container lifecycle.

Speaker B: So I should not put important database data there and assume it will survive forever.

Speaker A: Correct.

Speaker B: That's why volumes exist.

Speaker A: Yes.

Speaker B: So image, container, volume, network.

Speaker A: Those are four things I want you to separate.

Speaker B: The image is what we start from.

Speaker A: Good.

Speaker B: The container is the running process environment.

Speaker A: Good.

Speaker B: The volume gives data a place that can live outside the normal container layer.

Speaker A: Good.

Speaker B: The network controls how the container reaches other services.

Speaker A: Good.

Speaker B: What does an image contain?

Speaker A: Files needed to run the application, application code, runtime pieces, system libraries, and instructions for starting it.

Speaker B: And image layers help with reuse.

Speaker A: Yes. If many images share the same base layers, storage and transfer can be more efficient.

Speaker B: That sounds obvious now.

Speaker A: It becomes obvious after you see the problem.

Speaker B: Again, start from the problem.

Speaker A: Exactly.

Speaker B: Let's do a broken example.

Speaker A: Someone builds the application on a laptop. They install a newer runtime. The container uses an older runtime. The application fails inside the container.

Speaker B: So the container exposed an environment mismatch that the laptop hid.

Speaker A: Right.

Speaker B: Which is actually useful.

Speaker A: Very useful.

Speaker B: The container did not create the bug. It made the environment difference visible.

Speaker A: That's a good way to say it.

Speaker B: Another failure?

Speaker A: The app writes a file inside the container. The container restarts. The file is gone.

Speaker B: Not necessarily a bug. It may be the expected lifecycle.

Speaker A: Exactly.

Speaker B: If the file matters, use persistent storage.

Speaker A: Right.

Speaker B: Another one: the app listens on port 8080 inside the container, but the laptop cannot reach it.

Speaker A: What do you ask?

Speaker B: Is the container running?

Speaker A: Good.

Speaker B: Is the process listening?

Speaker A: Good.

Speaker B: Is the port published or connected through the right network?

Speaker A: Good.

Speaker B: Can we connect from the laptop?

Speaker A: Good.

Speaker B: Same debugging model again.

Speaker A: Exactly.

Speaker B: What about "port mapping"?

Speaker A: A simple case is mapping a host port to a container port. The application can listen on 8080 inside the container while the host exposes another port.

Speaker B: So the two sides can use different port numbers.

Speaker A: Yes.

Speaker B: Which means someone saying "the app runs on port 8080" is incomplete.

Speaker A: It depends on where you are standing.

Speaker B: That's going to be a course slogan.

Speaker A: Please don't put it on a T-shirt.

Speaker B: I might.

Speaker A: Fine.

Speaker B: Real-life example?

Speaker A: Think of an apartment building.

Speaker A: Each apartment has its own space. You do not walk through one apartment to get to another.

Speaker B: But they share the building structure.

Speaker A: Right.

Speaker B: So that's like containers sharing the host kernel.

Speaker A: Roughly.

Speaker A: Good.

Speaker B: So containers are built from real operating-system features.

Speaker A: Exactly.

Speaker B: Not tiny virtual machines.

Speaker A: Correct.
