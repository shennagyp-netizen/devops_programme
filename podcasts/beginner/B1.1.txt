Speaker A: Whether the web application is slow, one process is blocked, the machine is under pressure, the application is waiting on a database, or the network path is slow.

Speaker B: Make a prediction.

Speaker A: The screen is slow, but CPU usage on the application machine is low. Does that prove the machine is healthy?

Speaker A: Why?

Speaker B: The process could be waiting for a database, storage, a lock, or another network service.

Speaker A: Good. Low CPU can mean healthy idleness or expensive waiting.

Speaker B: So CPU is evidence, not a verdict.

Speaker A: Exactly.

Speaker B: Now the second box: Process.

Speaker A: A program is stored code. A process is that program running with state and resources.

Speaker B: So when I debug a slow service, I want to know which process is actually doing the work.

Speaker A: Yes.

Speaker B: Not just the application.

Speaker A: Correct. That name is often too broad.

Speaker B: What does the operating system manage for a process?

Speaker A: CPU time, memory, files, sockets, signals, permissions and other resources.

Speaker B: And a process has an identity.

Speaker A: A process ID, or PID.

Speaker A: Exactly.

Speaker B: First command?

Speaker A: Try:

Speaker A: ps aux | head

Speaker B: What am I looking for?

Speaker A: A process you recognize, its state, and useful resource numbers. Do not try to memorize every column.

Speaker B: What does process state mean?

Speaker A: It tells you something about what the process is doing at that moment. A process can be running, waiting, stopped, or gone. Linux exposes more detailed states, but the operational idea is simple: alive does not always mean working.

Speaker B: So a process can exist while doing very little CPU work.

Speaker A: Yes.

Speaker B: Because it may be waiting.

Speaker A: Exactly.

Speaker B: Now the third box: Resource.

Speaker A: Ask what the process is consuming or waiting for.

Speaker B: CPU.

Speaker A: Good.

Speaker B: Memory.

Speaker A: Good.

Speaker B: Files and storage.

Speaker A: Good.

Speaker B: Network sockets.

Speaker A: Good.

Speaker B: Locks and other synchronization.

Speaker A: Right. The point is not to collect every metric. Find the next observation that separates the likely causes.

Speaker B: Give me a trap.

Speaker A: The process uses very high CPU.

Speaker B: That means the app is broken.

Speaker A: Not necessarily.

Speaker B: Maybe the workload really increased.

Speaker A: Exactly.

Speaker B: So high CPU can be normal for a busy service.

Speaker A: Yes.

Speaker B: Another trap: CPU is only five percent.

Speaker A: That can still be a serious problem.

Speaker B: Because the process might be waiting on a dependency.

Speaker A: Exactly.

Speaker B: So both high and low CPU need context.

Speaker A: That is the habit.

Speaker B: What about memory?

Speaker A: Memory tells you how much memory is being used, but again, context matters. A cache can make memory usage look large. A process can grow unexpectedly. A machine can be under pressure even when one process looks normal.

Speaker B: So memory is another signal, not another verdict.

Speaker A: Exactly.

Speaker B: Now the dependency box.

Speaker A: Maybe.

Speaker A: Maybe.

Speaker B: File system.

Speaker A: Good.

Speaker A: Good enough for today.

Speaker B: So not just another dashboard.

Speaker A: Correct.

Speaker B: Example?

Speaker A: Suppose the API is slow and you suspect the database.

Speaker B: I might compare request latency with database latency.

Speaker A: Good.

Speaker B: Or inspect one slow request and see where its time went.

Speaker A: Good.

Speaker B: Or use a controlled local failure where I own the system.

Speaker A: Exactly.

Speaker A: Use a local test service you control.

Speaker B: Good.

Speaker A: Do not memorize yes or no.

Speaker B: Because the exact outcome depends on how the process was started and what is supervising it.

Speaker A: Exactly.
