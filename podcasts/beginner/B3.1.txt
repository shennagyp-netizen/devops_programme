EPISODE B3.1 — Why Use a Queue?

Speaker A: We have a new problem.

Speaker B: Of course.

Speaker A: The B3 app receives more work than one API process can finish immediately.

Speaker B: So we need a queue.

Speaker A: Maybe. First tell me what problem a queue would solve.

Speaker B: It separates receiving work from processing work.

Speaker A: Good.

Speaker B: The API can accept the request, put the work somewhere safe, and a worker handles it later.

Speaker A: Exactly.

Speaker B: Why is that useful?

Speaker A: Think about a restaurant.

Speaker B: Okay.

Speaker A: The waiter writes orders down.

Speaker B: The kitchen cooks them.

Speaker A: Exactly.

Speaker B: So the waiter is the producer.

Speaker A: Roughly.

Speaker B: The order queue holds the work.

Speaker A: Right.

Speaker B: The kitchen worker is the consumer.

Speaker A: Exactly.

Speaker B: Good.

Speaker A: Now let's map it to software.

Speaker B: Client sends request.

Speaker A: API accepts it.

Speaker B: API writes a message to the queue.

Speaker A: Worker reads the message.

Speaker B: Worker does the work.

Speaker A: Right, when the business flow allows asynchronous work.

Speaker B: That's the key. Not every operation can be delayed.

Speaker A: Correct.
