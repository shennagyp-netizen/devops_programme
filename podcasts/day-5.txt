EPISODE D5.1 — Scaling

Speaker A: Scaling is one of the easiest words to say and one of the easiest engineering problems to misunderstand.

Speaker B: Because people hear scaling and think add servers.

Speaker A: Exactly. The real question is: where is capacity constrained, and how does more capacity change the whole system?

Speaker B: The picture is:

Speaker A: Workload -> Capacity -> Distribution -> Shared State -> Bottleneck -> Evidence.

Speaker B: That already sounds better than vertical versus horizontal.

Speaker A: We will still learn vertical and horizontal scaling. But those are actions. The system model comes first.

Speaker B: Start with workload.

Speaker A: Demand arrives over time. Requests per second. Concurrent users. Jobs per minute. Messages per second.

Speaker B: And demand is not constant.

Speaker A: Right. A normal hour and a traffic spike can be completely different operating conditions.

Speaker B: Prediction.

Speaker A: We double the number of web servers. Traffic also doubles at the same time. Should latency automatically improve?

Speaker B: No. The new servers only help if the constrained part of the request path can use the extra capacity.

Speaker A: Exactly.

Speaker B: Stage two: capacity.

Speaker A: Every component has limits.

Speaker B: CPU.

Speaker A: Yes.

Speaker B: Memory.

Speaker A: Yes.

Speaker B: Database connections.

Speaker A: Yes.

Speaker B: Network bandwidth.

Speaker A: Yes.

Speaker B: Lock throughput. Disk I/O. External API rate limits.

Speaker A: Exactly. Capacity belongs to the dependency graph, not just the server.

Speaker B: Vertical scaling means making one capacity unit larger.

Speaker A: Correct.

Speaker B: Horizontal scaling means adding more units.

Speaker A: Correct.

Speaker B: Neither changes the other limits automatically.

Speaker A: Exactly.

Speaker B: Real-life example?

Speaker A: One supermarket cashier can serve customers faster if you improve the checkout station.

Speaker B: Vertical scaling.

Speaker A: Or you open more checkout lanes.

Speaker B: Horizontal scaling.

Speaker A: But if all lanes depend on one payment terminal or one manager approving every transaction, opening more lanes may not solve the bottleneck.

Speaker B: Shared state or shared dependency.

Speaker A: Exactly.

Speaker B: Stage three: distribution.

Speaker A: Once you have more capacity units, work has to reach them.

Speaker B: Load balancer.

Speaker A: One example.

Speaker B: Queue.

Speaker A: Another.

Speaker B: Partitioning.

Speaker A: Another.

Speaker B: So adding servers without a useful distribution path can leave one server busy and the rest idle.

Speaker A: Exactly.

Speaker B: Prediction.

Speaker A: We add four API servers, but almost all requests still hit one instance. What do you inspect?

Speaker B: Load balancing, session affinity, routing rules, health state and whether the instances are actually eligible for traffic.

Speaker A: Good.

Speaker B: So horizontal scaling needs a distribution mechanism.

Speaker A: Usually, yes.

Speaker B: Stage four: shared state.

Speaker A: Stateless services are easier to distribute because any healthy instance can handle the next request without private state from one specific server.

Speaker B: Sessions are the classic example.

Speaker A: Yes. If session state exists only in one instance's memory, a request sent to another instance may behave differently.

Speaker B: Put the state in a shared store, use a suitable session strategy, or redesign the request flow.

Speaker A: Exactly. The point is not that every system must be stateless. The point is to know where state lives and whether it limits distribution.

Speaker B: Another shared state example?

Speaker A: A database.

Speaker B: Every web server sends more queries to the same database.

Speaker A: Right.

Speaker B: So doubling web servers can move pressure into the database instead of reducing end-to-end latency.

Speaker A: Exactly.

Speaker B: That brings us to the fifth box: bottleneck.

Speaker A: The active bottleneck is the dependency that limits useful end-to-end capacity at that moment.

Speaker B: And the bottleneck can move after a scaling action.

Speaker A: That is one of the most important scaling ideas.

Speaker B: Prediction.

Speaker A: We double the web servers and latency barely changes. What are your first hypotheses?

Speaker B: Database latency. Database connection saturation. Cache behavior. Network limits. Downstream APIs. Lock contention. A load-balancer problem.

Speaker A: Good. Notice what you did not say.

Speaker B: Add more web servers again.

Speaker A: Exactly.

Speaker B: Now imagine the database was already at 80 percent capacity and each new web server adds more concurrent database work.

Speaker A: What happens?

Speaker B: The database can become the new bottleneck or get worse, even though web CPU falls.

Speaker A: Exactly.

Speaker B: So lower CPU on the web tier can coexist with worse user latency.

Speaker A: Yes. That is why one metric is never the whole scaling story.

Speaker B: What about queues and caches?

Speaker A: They can absorb bursts or reduce repeated work.

Speaker B: Which sounds like free capacity.

Speaker A: It is not free.

Speaker B: Because they have their own limits.

Speaker A: Exactly. A cache can miss. A queue can fill. A full queue changes latency or causes rejection.

Speaker B: So buffers move the time of failure, not eliminate the limit.

Speaker A: Excellent.

Speaker B: Stage six: evidence.

Speaker A: We measure before and after the scaling action.

Speaker B: Request rate.

Speaker A: Good.

Speaker B: Latency distribution.

Speaker A: Good.

Speaker B: Error rate.

Speaker A: Good.

Speaker B: Saturation of the first constrained dependency.

Speaker A: Good.

Speaker B: And the real user path.

Speaker A: Exactly.

Speaker B: So scaling is not proved by 'we now have eight replicas.'

Speaker A: Correct.

Speaker B: It is proved by system behavior under the workload we care about.

Speaker A: Exactly.

Speaker B: Controlled experiment?

Speaker A: Start with a tiny application and one known request path.

Speaker B: Measure baseline throughput and latency.

Speaker A: Good.

Speaker B: Add a second application instance.

Speaker A: Good.

Speaker B: Increase workload in a controlled way.

Speaker A: Good.

Speaker B: Observe where latency or errors rise first.

Speaker A: Good.

Speaker B: Then make one change to the suspected bottleneck.

Speaker A: Good.

Speaker B: For example, increase database connection capacity in a safe environment, or reduce query cost, or add cache coverage.

Speaker A: Exactly. Pick one change.

Speaker B: Then repeat the same workload.

Speaker A: And compare the evidence.

Speaker B: Did the bottleneck move? Did user latency improve? Did another dependency saturate?

Speaker A: Good.

Speaker B: This is basically a paper load test made executable.

Speaker A: Right. You do not need Kubernetes autoscaling to learn the mechanism.

Speaker B: What about statelessness in the lab?

Speaker A: Make one request path that can move between two application instances.

Speaker B: Then introduce private in-memory session state.

Speaker A: Good.

Speaker B: Send the next request to the other instance.

Speaker A: What should you predict?

Speaker B: The session may disappear or behave inconsistently because the second instance cannot see the first instance's private state.

Speaker A: Exactly.

Speaker B: Then move that state to a shared store.

Speaker A: And verify that the request path becomes portable across instances.

Speaker B: Nice.

Speaker A: One more important rule: scale the bottleneck, not the part you can see most easily.

Speaker B: So a CPU graph is not the scaling plan.

Speaker A: Correct.

Speaker B: And average latency is not enough either.

Speaker A: Correct.

Speaker B: Tail latency can stay terrible even when the average looks better.

Speaker A: Exactly. Choose measurements that match the user experience and workload shape.

Speaker B: Recall.

Speaker A: Vertical scaling?

Speaker B: Make one capacity unit larger.

Speaker A: Horizontal scaling?

Speaker B: Add more units and distribute work among them.

Speaker A: Why does statelessness help?

Speaker B: Requests can move between instances without depending on private in-memory state in one instance.

Speaker A: Why can adding servers fail to improve latency?

Speaker B: Another dependency can be the bottleneck, or distribution and shared state can prevent useful parallel work.

Speaker A: What do queues and caches change?

Speaker B: They can absorb bursts or reduce repeated work, but they introduce their own limits and failure modes.

Speaker A: What proves scaling worked?

Speaker B: Evidence that the relevant user path has better capacity, latency or throughput under the workload we care about, without just moving the bottleneck somewhere else.

Speaker A: Final challenge.

Speaker B: Traffic doubles. We double web servers. Latency barely changes.

Speaker A: Your model?

Speaker B: Workload -> Capacity -> Distribution -> Shared State -> Bottleneck -> Evidence. I identify the first constrained dependency, check whether work is actually distributed, inspect shared state, and measure the real user path before adding more capacity.

Speaker A: Good.

Speaker B: So scaling is not adding servers.

Speaker A: It is changing capacity at the right boundary and proving that the whole system benefits.

Speaker B: Run the lab, find the first bottleneck, move it once, and measure what moved next.

EPISODE D5.2 — Databases at Scale

Speaker A: Scaling a database is harder than adding more application servers.

Speaker B: Because the database also has to stay correct.

Speaker A: Exactly. The visual is:

Speaker B: Query -> Access Path -> Correctness -> Copies -> Distribution -> Evidence.

Speaker A: Start with the query.

Speaker B: What data does the application need? How many reads? How many writes? How much data? How many concurrent operations?

Speaker A: Good. Before choosing an index or a replica, understand the workload.

Speaker B: Prediction.

Speaker A: A table grows from one million rows to one hundred million. The application sends the same query. Should we assume the query cost stays the same?

Speaker B: No. The data size and access path may make the query much more expensive.

Speaker A: Exactly.

Speaker B: Stage two: access path.

Speaker A: An index can let the database find relevant rows without scanning the whole table.

Speaker B: But an index is not free.

Speaker A: Correct. It takes storage and adds work to writes and index maintenance.

Speaker B: So the right question is not 'Can I add an index?'

Speaker A: It is 'What access path does this workload need, and what does the index cost?'

Speaker B: Query plan becomes evidence.

Speaker A: Exactly.

Speaker B: Prediction.

Speaker A: We add an index and the query gets faster, but write latency increases.

Speaker B: That is possible because the database now has more index maintenance work on writes.

Speaker A: Good.

Speaker B: So one optimization can move the bottleneck.

Speaker A: Same scaling lesson as before.

Speaker B: Stage three: correctness.

Speaker A: Databases run many operations at the same time.

Speaker B: Transactions give us a controlled unit of work.

Speaker A: Yes.

Speaker B: And concurrency control decides how those operations interact.

Speaker A: Exactly. MVCC is one common model for letting readers and writers work with consistent versions without forcing every operation to block every other operation.

Speaker B: So scaling database work can never ignore correctness.

Speaker A: Right.

Speaker B: Give me a race.

Speaker A: Two users try to buy the last item at the same time.

Speaker B: If the database logic is wrong, both requests can believe the item is available.

Speaker A: Exactly.

Speaker B: A faster database that sells one item twice is not a successful scaling result.

Speaker A: Very important.

Speaker B: Prediction.

Speaker A: We add more application workers without changing the transaction logic. Can concurrency problems get worse?

Speaker B: Yes. More workers can create more concurrent database operations and expose a race that was rare at lower load.

Speaker A: Exactly.

Speaker B: Stage four: copies.

Speaker A: Replication creates additional copies of database data.

Speaker B: Useful for read capacity, availability or data locality.

Speaker A: Yes.

Speaker B: But copies can lag.

Speaker A: Exactly.

Speaker B: So a replica can be healthy and still be behind the primary.

Speaker A: Correct.

Speaker B: Prediction.

Speaker A: A user writes a new order, then immediately reads from a replica. Is the newest order guaranteed to be there?

Speaker B: Not unless the system's consistency rules guarantee that read sees the newest committed write.

Speaker A: Good.

Speaker B: So replication creates a consistency choice, not just a speed button.

Speaker A: Exactly.

Speaker B: Stage five: distribution.

Speaker A: Partitioning divides data into regions according to a key or other rule.

Speaker B: Sharding takes that idea further by distributing partitions across separate database nodes.

Speaker A: Yes. The exact architecture varies, but the key change is that data ownership and work are no longer in one place.

Speaker B: Which can improve scale.

Speaker A: And create new coordination cost.

Speaker B: A query for one user may touch one partition.

Speaker A: While a report across all users may touch many partitions.

Speaker B: So partitioning can make one query much better and another much harder.

Speaker A: Exactly.

Speaker B: Prediction.

Speaker A: A query used to scan one table. After sharding, the query must ask twelve shards and combine the results. Did the database automatically become simpler?

Speaker B: No. The system may have more write or data capacity, but the query now has a distributed coordination cost.

Speaker A: Good.

Speaker B: Now put the path together.

Speaker A: Query.

Speaker B: Access path.

Speaker A: Correctness.

Speaker B: Copies.

Speaker A: Distribution.

Speaker B: Evidence.

Speaker A: Exactly.

Speaker B: Every scaling mechanism answers a different question.

Speaker A: Index.

Speaker B: Find data more efficiently.

Speaker A: Transaction and concurrency control.

Speaker B: Keep concurrent work correct.

Speaker A: Replication.

Speaker B: Add copies for selected capacity or availability goals.

Speaker A: Partitioning and sharding.

Speaker B: Distribute data ownership and work.

Speaker A: Good.

Speaker B: Now the failure cases.

Speaker A: Query is slow.

Speaker B: Inspect the query plan and data access path before adding replicas.

Speaker A: Write latency is high after adding an index.

Speaker B: Inspect index maintenance cost.

Speaker A: Read is stale after a successful write.

Speaker B: Inspect replica lag and the consistency contract.

Speaker A: A cross-shard report is slow.

Speaker B: Inspect partition count, data movement and coordination cost.

Speaker A: Two users buy the last item.

Speaker B: Inspect transaction boundaries, locks, isolation behavior and the data invariant.

Speaker A: Exactly.

Speaker B: Evidence before mechanism.

Speaker A: Every time.

Speaker B: Controlled lab?

Speaker A: Start with a small dataset and one slow query.

Speaker B: Measure baseline latency.

Speaker A: Good.

Speaker B: Add one appropriate index.

Speaker A: Predict what should improve and what could get worse.

Speaker B: Re-run the query and inspect the plan.

Speaker A: Good.

Speaker B: Then simulate or create a read replica in a safe environment.

Speaker A: Test a write followed by a read and record what consistency behavior you see.

Speaker B: Then model partitioning with a larger dataset.

Speaker A: Good.

Speaker B: Compare a query that stays within one partition with one that crosses many partitions.

Speaker A: Exactly.

Speaker B: What should I write down?

Speaker A: Workload. Baseline. Change. Expected benefit. New cost. Evidence. Correctness risk. Recovery.

Speaker B: That is a much better database lab than 'create a replica.'

Speaker A: It teaches why the mechanism exists.

Speaker B: Recall.

Speaker A: Why can an index help?

Speaker B: It can reduce the data the database must inspect for a query.

Speaker A: What does the index cost?

Speaker B: Storage and extra work when data changes.

Speaker A: What is replication?

Speaker B: Keeping additional copies of data on other database members for goals such as read scale, availability or locality.

Speaker A: What is the main new risk?

Speaker B: Replicas can lag and reads may not see the newest write unless the consistency rules guarantee it.

Speaker A: What is partitioning?

Speaker B: Dividing data into regions so work can be scoped or distributed.

Speaker A: What does sharding add?

Speaker B: It distributes those regions across separate nodes, which can increase capacity but also adds coordination and cross-shard query cost.

Speaker A: Final challenge.

Speaker B: The query is slow. We add an index. Reads improve, but writes slow down. Then we add replicas and some users see stale data.

Speaker A: Your model?

Speaker B: Query -> Access Path -> Correctness -> Copies -> Distribution -> Evidence. I measure the query plan, index cost, write behavior, replica freshness and the actual user path before deciding what to change next.

Speaker A: Good.

Speaker B: So database scaling is not a shopping list.

Speaker A: It is a set of mechanisms with correctness and coordination costs.

Speaker B: Run the lab, make one change at a time, and explain both the gain and the new responsibility.


EPISODE D5.3 — Distributed Systems

Speaker A: The central difficulty of distributed systems is partial failure. One machine can be healthy while the network path to it is broken.

Speaker B: Which means 'the server is up' can be completely useless.

Speaker A: Correct.

Speaker A: Real-life analogy: imagine several branches of the same company that cannot reliably call each other. Each branch knows some facts, but not necessarily the latest facts.

Speaker A: That makes replication, consistency, quorum, ordering, and timeouts fundamental.

Speaker A: Joke: distributed systems are where two computers finally discover that communication is hard.

Speaker B: Very philosophical for a Tuesday.

Speaker A: And annoyingly expensive when true.

Speaker A: Lab: design what users see when one replica is delayed, unavailable, or partitioned.
Speaker B: Distributed systems are basically “the computer is no longer one thing.”

Speaker A: That's a good opening.

Speaker B: Partial failure feels like the big idea.

Speaker A: It is. One node can be healthy while another is unreachable. One request can succeed while its caller times out. Two replicas can temporarily disagree.

Speaker B: Real-life example?

Speaker A: Two branches of the same company lose their phone connection to each other. Each branch is still open. Neither knows exactly what the other has done in the last hour.

Speaker B: Humans can survive that. Computers get very upset.

Speaker A: Computers are excellent at arithmetic and surprisingly bad at uncertainty.

Speaker B: Prediction. Service A sends a request to Service B. B completes the operation, but A times out waiting. What does A know?

Speaker A: Only that it didn't observe the response within its deadline. It does not automatically know whether B failed, succeeded, or succeeded and the response was lost.

Speaker B: Which is why blind retries can duplicate work.

Speaker A: Exactly. This is where idempotency and careful retry policy become crucial.

Speaker B: Mac exercise?

Speaker A: Write a tiny mental distributed system with two services. Introduce a one-way delay or dropped response in your model. Then list what each side knows at each step. You're learning to reason about incomplete information.

Speaker B: That's much more fundamental than memorizing CAP slogans.

Speaker A: Much more.


EPISODE D5.4 — Reliability Patterns

Speaker A: Reliability patterns exist because a failure in one component can trigger more work than the system can handle.

Speaker B: Retry sounds friendly until everyone retries at once.

Speaker A: Exactly. That is a retry storm.

Speaker A: Imagine a restaurant phone that rings because an order failed. If every caller retries every second, the failure becomes worse. Exponential backoff and jitter spread retries over time.

Speaker A: Idempotency makes repeated operations safer. Circuit breakers stop calls to unhealthy dependencies. Backpressure prevents unlimited work from entering an overloaded system.

Speaker A: Real-life example: a delivery company may safely retry 'check delivery status' many times, but a blind retry of 'charge this credit card' needs much more careful semantics.

Speaker A: Lab: simulate a slow dependency and compare fixed retries with exponential backoff and a circuit breaker.
Speaker B: Reliability patterns are all about what happens when things don't behave like the happy path.

Speaker A: Right. Timeout means stop waiting after a bounded period. Retry means try again. Backoff slows repeated attempts. Jitter prevents synchronized retries. Idempotency makes repeated requests safer. Backpressure prevents overloaded systems from accepting more work than they can handle.

Speaker B: The dangerous part is combining them carelessly.

Speaker A: Exactly. A retry storm can turn a struggling dependency into a dead dependency.

Speaker B: Restaurant example?

Speaker A: Ten customers call because their delivery order hasn't arrived. The restaurant is overwhelmed, so every customer calls again every five seconds. Now the phone system itself becomes another failure source.

Speaker B: That's basically a retry storm.

Speaker A: Yes.

Speaker B: Prediction. Two services both retry aggressively with the same delay.

Speaker A: What happens under widespread failure?

Speaker B: Their retries synchronize. Load spikes exactly when the dependency is already struggling.

Speaker A: Good. Jitter exists for a reason.

Speaker B: Mac exercise?

Speaker A: Write a tiny retry policy on paper. Give it a timeout, maximum attempts, backoff, and jitter range. Then calculate how much traffic it creates when one hundred callers hit a failed dependency.

Speaker B: That turns “resilience” into arithmetic.

Speaker A: It should. Reliability is an engineering discipline, not a mood.


EPISODE D5.5 — Observability

Speaker A: Production systems cannot be managed by vibes.

Speaker B: Finally, a formal definition of engineering.

Speaker A: Logs record events. Metrics quantify behavior. Traces show causal paths across services.

Speaker A: Think of a traffic control room. Cameras show events. Counters show volume. A map traces a vehicle's route. You need all three views to understand congestion.

Speaker A: SLI measures a behavior. SLO states a target. Error budget expresses how much unreliability is acceptable.

Speaker A: Real-life example: if users report 'the site feels slow,' one good metric like CPU might not explain it. You need latency, error rate, dependency timing, traces, and workload context.

Speaker A: Lab: define one SLI, an SLO, an alert, and a trace path for the application.
Speaker B: Observability is where all the evidence we've been collecting gets organized.

Speaker A: Exactly. Logs tell stories. Metrics summarize behavior over time. Traces connect work across components.

Speaker B: And SLI and SLO stop it from becoming a dashboard collection hobby.

Speaker A: Right. An SLI is a measured indicator of service behavior. An SLO sets a target. An error budget connects reliability work to a defined tolerance for failure.

Speaker B: Traffic control room analogy?

Speaker A: A traffic control room doesn't display every possible sensor just because it can. It highlights the signals needed to detect congestion, incidents, and changes in flow.

Speaker B: Prediction. CPU is normal, but user latency is terrible.

Speaker A: What does that tell you?

Speaker B: CPU isn't the dominant bottleneck. I need to inspect dependencies, queues, network, database, lock contention, or maybe tail latency.

Speaker A: Good. Observability helps you ask which hypothesis fits the evidence.

Speaker B: And high-cardinality labels can become their own problem.

Speaker A: Exactly. Instrumentation has cost and design trade-offs.

Speaker B: Mac exercise?

Speaker A: Take one request through a hypothetical web service and name the logs, metrics, and trace spans you'd want. Then remove half the signals and ask what diagnosis becomes harder.

Speaker B: So observability design starts from questions.

Speaker A: Always. Instrumentation should answer operational questions.


EPISODE D5.6 — Disaster Recovery

Speaker A: A backup is not a recovery strategy until you can restore from it.

Speaker B: Painfully true.

Speaker A: RPO asks how much data loss is acceptable. RTO asks how long recovery may take.

Speaker A: Real-life analogy: a fire extinguisher is equipment; a fire drill is an operational capability.

Speaker A: Multi-AZ and multi-region architectures reduce different classes of failure. More redundancy also means more complexity and cost.

Speaker A: Real-life example: a business that can survive a server outage but not a regional outage has two different recovery problems.

Speaker A: Lab: write a restore procedure and calculate whether it meets a stated RPO and RTO.
Speaker B: Disaster recovery is one of those things everyone approves until someone asks when the last restore test happened.

Speaker A: Exactly.

Speaker B: RPO is how much data loss you can tolerate. RTO is how long recovery can take.

Speaker A: Right.

Speaker B: Backup is not recovery.

Speaker A: That's the line to remember.

Speaker B: Fire extinguisher versus fire drill?

Speaker A: Perfect. Owning a fire extinguisher does not prove that the building can be evacuated. A backup file existing does not prove you can restore the service, the dependencies, the credentials, and the application state correctly.

Speaker B: Prediction. The database backup is valid, but the application can't start in the recovery environment.

Speaker A: Then the database backup didn't solve the incident. The recovery system is incomplete.

Speaker B: So DR is a system.

Speaker A: Exactly. Data, infrastructure, configuration, identity, dependencies, runbooks, and people.

Speaker B: Mac exercise?

Speaker A: Write an RPO and RTO for a fictional service. Then design a restore test. Don't just say “restore the backup.” State what evidence proves the service is actually usable.

Speaker B: That's uncomfortable.

Speaker A: Recovery planning should make you uncomfortable before the incident does.


EPISODE D5.7 — Global-Scale Architecture

Speaker A: Now we combine everything. A global system needs traffic distribution, compute, data, cache, queues, observability, identity, security, and recovery.

Speaker B: And the fun part is that every decision changes another decision.

Speaker A: Exactly. This is architecture as a dependency graph.

Speaker A: Real-life example: international airports do not simply add more gates. They need runways, terminals, baggage systems, security, traffic routing, emergency procedures, and regional coordination.

Speaker A: For a global software system, ask where users enter, where data lives, which failures are isolated, what is cached, what is asynchronous, and what can degrade gracefully.

Speaker A: Lab: design a multi-region architecture for millions of users and explain every major failure domain.
Speaker B: Global scale adds geography to every previous problem.

Speaker A: And latency.

Speaker B: And failure domains.

Speaker A: And data sovereignty, routing, replication, deployment, capacity planning.

Speaker B: Airport analogy?

Speaker A: Think about an international airport system. You might have regional hubs, local feeder routes, traffic control, baggage systems, security, and alternate airports. A global application has analogous layers, though the mechanisms are different.

Speaker B: Prediction. If one region fails, should traffic automatically move to another region?

Speaker A: Only if the architecture, data model, routing, capacity, and recovery design make that safe.

Speaker B: So “multi-region” is not one checkbox.

Speaker A: Exactly. You can have two regions and still have one logical bottleneck.

Speaker B: Mac exercise?

Speaker A: Draw a two-region web service. Mark where users enter, where sessions live, where writes go, how data replicates, and what happens when one region disappears. Then calculate whether the surviving region has enough capacity.

Speaker B: The last part is easy to forget.

Speaker A: And that forgotten part is how failover becomes a second outage.


EPISODE D5.8 — The Production Incident
