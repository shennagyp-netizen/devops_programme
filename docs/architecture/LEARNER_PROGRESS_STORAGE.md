# Learner Progress History

## Purpose

The database stores **completion history**, not terminal history.

A learner may complete lessons, assignments, questions, and projects in any order. The system records the learner's real completion path and does not require the authored curriculum order.

The persistent identity is:

`authenticated user + item type + item ID`

There is exactly one persistent completion row for that combination.

## Authoritative architecture

The learner-facing application is a Next.js App Router application with Clerk authentication, Drizzle ORM, and PostgreSQL.

The normal completion path is:

```text
Interactive SPA shell
      |
      v
Next.js Server Action
      |
      v
Clerk authenticated user ID
      |
      v
Drizzle ORM
      |
      v
PostgreSQL
```

There is no learner-progress REST API.

The browser never chooses the learner identity.

## Stored row

Table:

`learner_progress_history`

Columns:

- `id`
- `user_id`
- `item_type`
- `item_id`
- `course`
- `project_id`
- `verification_level`
- `completed_at`

The unique identity is:

`user_id + item_type + item_id`

PostgreSQL also enforces that `item_type` is one of:

- `lesson`
- `assignment`
- `question`
- `project`

## History order

`completed_at` is generated by the server/database.

The server reads completion history in ascending:

1. `completed_at`
2. `id` as a deterministic tie-breaker.

Example:

```text
10:12  D2.4
10:21  D1.3
10:46  D4.1
11:02  B1.2
```

This is the learner's actual path, not the authored course order.

## Completion semantics

Completion is append-once and idempotent.

When a learner completes an item:

1. Clerk supplies the authenticated user ID.
2. The Server Action validates the completion input.
3. Drizzle inserts one row.
4. PostgreSQL ignores a duplicate user/item completion.
5. The original `completed_at` is preserved.

There is no uncomplete operation.

Repeated completion does not create another row and does not rewrite the original completion timestamp.

## Input contract

The browser may submit only:

- `item_type`
- `item_id`
- optional `course`
- optional `project_id`
- optional `verification_level`

The browser may not submit the user identity as an authority.

Unknown fields are ignored by the completion parser.

The completion parser rejects:

- missing item type
- unsupported item type
- missing item ID
- oversized values.

The same item-type invariant is enforced again by PostgreSQL.

## What is not stored

The progress database does **not** store:

- terminal stdout
- terminal stderr
- command history
- failed attempts
- retries
- machine-output dumps
- raw machine-verification envelopes
- intermediate UI interactions
- browser-generated learner UUIDs.

Terminal output remains transient UI state and is discarded after the current verification flow.

## Authentication and user management

Authentication is handled by Clerk.

The application uses:

- Clerk sign-up
- Clerk sign-in
- Clerk session state
- Clerk `UserButton`

The `UserButton` supplies account management and sign-out without a custom user-management API.

Clerk is therefore the identity authority. PostgreSQL stores the application-specific learning history keyed by the Clerk user ID.

## Environment

Required runtime configuration:

```text
DATABASE_URL=...
NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=...
CLERK_SECRET_KEY=...
```

Secrets must never be committed.

## TDD contract

The architecture is protected by tests before implementation.

Unit tests cover the completion input boundary.

Integration tests cover the Server Action boundary:

- unauthenticated requests fail closed
- Clerk user ID is authoritative
- browser-supplied learner identity is ignored
- terminal output is not forwarded
- only supported completion metadata reaches the server service.

The repository architecture contract also verifies that the old Vite bootstrap, anonymous learner storage, and progress REST API are absent.

Hosted CI remains a separate verification boundary and must not be called green without an executed runner result.
